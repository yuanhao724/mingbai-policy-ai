# 明白办事 · 作品集技术说明

## 30 秒介绍

明白办事是一个面向社区政策场景的 AI 应用。它把政策原文翻译成一张能照着办的「明白卡」：谁能办、能领什么、要带什么、怎么办、什么时候截止、常见坑。每个结论都带原文引用，问答锁定当前政策，AI 生成结果需要人工审核，所有审核动作写入审计日志。

它不是通用聊天框，也不是只展示模型能力的 Demo。它有一条完整的工程闭环：

```text
上传政策
  → 段落感知切块
  → 字符 n-gram TF-IDF 检索
  → 意图识别 + 范围护栏
  → 结构化明白卡 + 原文引用
  → SSE 流式问答
  → 人工审核 + 审计日志
  → 离线评测 + Prometheus 指标
```

## 问题与用户

### 用户

- 社区居民，尤其是老年人和新市民。
- 社区窗口工作者。
- 政策运营和审核人员。

### 真实痛点

1. 政策不是没有，是看不懂。关键条件藏在术语、附件和长段落里。
2. 材料清单分散，少带一样就要再跑一趟。
3. 同一个问题，窗口每天要回答几十遍，经验留在个人脑子里。
4. AI 生成的政策解释如果不可追溯，会带来误导风险。

### 产品判断

这个场景需要的不是「更大的模型」，而是「更窄的工作流 + 可追溯的证据 + 人工兜底」。

## 范围与非目标

### 当前范围

- 单政策卡片生成和单政策问答。
- 本地可跑的抽取式回答。
- 可选 OpenAI 在线模式。
- 材料清单、导出、打印、大字和朗读。
- 人工审核、审计日志、离线评测和基础可观测性。

### 明确不做

- 不提供法律、医疗、投资结论。
- 不把示例政策当作官方政策。
- 不在没有人工审核的情况下自动发布政策卡。
- 不追求一次性支持所有城市的全部政策。

## 架构

```text
Browser
  │ fetch + SSE
  ▼
FastAPI
  ├─ Middleware
  │   ├─ request ID + structured log + Prometheus
  │   ├─ token-bucket rate limit
  │   └─ security headers + CSP
  ├─ /api/documents   上传、解码、切块、入库、删除
  ├─ /api/policy     政策原文 → 明白卡
  ├─ /api/chat       当前政策检索 + 意图识别 + SSE
  ├─ /api/reviews    人工审核 + 审计日志
  ├─ /api/eval       最新离线评测报告
  └─ /api/metrics    Prometheus 文本指标
  │
  ├─ SQLite：documents / chunks / queries / audit_logs
  ├─ scikit-learn：字符 2-3 gram TF-IDF
  └─ OpenAI（可选）：chat completions
```

## 数据模型

| 表 | 作用 |
| --- | --- |
| documents | 政策原文、文件信息、审核状态、审核人 |
| chunks | 段落感知切块，保留原文顺序 |
| queries | 问题、回答、模式、来源、延迟 |
| audit_logs | 审核动作、操作者、目标、备注 |

审核字段：

- `review_status`：draft / approved / rejected。
- `reviewer`：审核人。
- `reviewed_at`：审核时间。

## 关键设计

### 1. 单政策上下文

问答先校验 `doc_id`，只取当前政策的片段。这样避免「问高龄津贴，答成公租房」的跨政策串答。

### 2. 稳定引用

检索分数只用于排序，上下文按原文 `ord` 顺序编号。回答里的 `[n]` 和右侧来源面板共用同一套编号，点击即可核对原文。

### 3. 中文检索 + 意图识别 + 拒答

- 检索：字符 2-3 gram TF-IDF，不依赖分词器和向量库，离线可跑。
- 意图：材料、流程、时限、待遇、条件、注意事项、咨询方式。
- 兜底：口语问句零命中时，回退当前政策全文，再按意图抽取字段。
- 拒答：跨域问题没有内容重叠时，不根据常识猜测。

### 4. 结构化明白卡

`policy.py` 使用标题、列表和字段关键词做混合抽取：

- 谁能办
- 能领什么
- 要带什么
- 怎么办
- 什么时候截止
- 常见坑
- 找谁问

每个字段都附引用片段，便于人工核对。

### 5. 双模式降级

- 无 `OPENAI_API_KEY`：本地抽取式回答，离线可跑。
- 有 Key：在线模型回答，SSE 流式返回。
- 在线模型失败：自动回退本地模式，演示不中断。

### 6. 人工审核与审计

AI 生成的政策卡不能直接发布。上传后的政策默认是 `draft`，审核员在审核台标记通过或驳回，所有动作写入 `audit_logs`。

演示环境用 `X-Mori-Role: reviewer` 模拟角色。生产环境应接入 SSO、RBAC 和更细粒度权限，不能把角色头当作真实鉴权。

## 评测

### 数据集

- 32 条问题。
- 28 条可回答。
- 4 条跨域拒答。
- 覆盖 4 份政策，每份包含材料、时限、待遇、条件、流程、注意事项、咨询方式。

### 指标

| 指标 | 含义 | 当前结果 |
| --- | --- | --- |
| Hit@1 | Top1 检索片段命中预期关键词 | 85.7% |
| Hit@3 | Top3 检索片段命中预期关键词 | 100% |
| MRR | 首个相关片段的平均倒数排名 | 0.929 |
| 关键词召回 | 回答覆盖预期事实关键词 | 100% |
| 引用有效率 | 引用编号不越界 | 100% |
| 引用覆盖率 | 可回答问题的回答至少有一个引用 | 100% |
| 引用支撑率 | 被引用片段包含预期信息 | 100% |
| Groundedness 代理 | 回答句子与原文的字符重合 | 100% |
| 拒答准确率 | 跨域问题不猜测 | 100% |
| P50 / P95 | 本地抽取链路延迟 | 约 0.6 / 1.3 ms（单次运行） |

### 诚实口径

- 当前是抽取式基线，回答直接来自原文，所以 Groundedness 偏高，不能把它当成「模型不会幻觉」的证明。
- 4 条 Top1 未命中，但 Top3 命中，仍能支撑回答。评测页单独展示了这些样例。
- 32 条是小样本，正式上线前需要扩大到 200 条以上并做人工事实核查。
- 延迟只包含本地检索和抽取，不包含浏览器渲染和网络。

## 可观测性

- 每个请求有 `X-Request-ID`。
- 结构化 JSON 日志包含 method、path、status、duration。
- `/api/metrics` 输出 Prometheus 文本格式的请求计数和延迟直方图。
- `/api/live` 和 `/api/ready` 分离存活和就绪检查。
- `/api/metrics` 不在限流范围内，便于监控采集。

## 安全

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy`
- CSP 限制 external script 和 external resource。
- 上传大小限制、文件名后缀限制、参数化 SQL。
- 限流默认 240 请求/分钟/IP，生产建议 Redis 或边缘限流。
- 不在日志中记录用户问题全文；密钥只从环境变量读取。

## 交付与部署

- 本地：`python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`
- Docker：`docker compose up --build`
- 测试：`cd backend && MORI_STREAM_DELAY=0 python -m unittest discover -s tests -v`
- 评测：`cd backend && python eval/run_eval.py --check`
- CI：GitHub Actions 在 3.11 / 3.12 / 3.13 上跑测试、评测和 Docker build。

## 关键取舍

| 选择 | 原因 |
| --- | --- |
| SQLite 而不是 Postgres | 单机 MVP 零配置，便于演示；生产换 Postgres |
| TF-IDF 而不是向量库 | 离线可用、可解释、启动快；下一步做混合检索 |
| 抽取式本地兜底 | 没有 API Key 也能演示，失败不中断 |
| 规则 + LLM 混合 | 规则保证稳定和引用，LLM 提升自然度 |
| 单政策上下文 | 先解决串答和引用一致，再考虑多政策对比 |
| 人工审核 | 政策解释有误导风险，AI 不能直接发布 |

## 如果继续做大

1. 把评测集扩到 200 条，加入人工事实核查和盲评。
2. 接入真实官方政策库，增加版本管理和失效提醒。
3. 检索升级为 BM25 + 向量混合，加 reranker。
4. 支持 PDF、扫描件和多政策对比。
5. 接入 SSO、RBAC、审核队列和发布工作流。
6. Postgres + Redis + 对象存储 + 异步任务。
7. 社区试点，跟踪材料漏带率、窗口重复咨询量、居民完成率。

## 面试问答

### 为什么不用向量数据库？

这个规模先用字符 n-gram TF-IDF 能离线跑、可解释、启动快。数据量上来后，我会做 BM25 + 向量混合，并用评测集决定是否值得引入向量库。

### 怎么保证引用不串？

问答锁定 `doc_id`，上下文按原文顺序编号，检索分数只用于排序；引用编号和来源面板共用同一套索引。

### 为什么 Groundedness 是 100%？

因为当前本地模式是抽取式回答，回答直接来自原文。这是一个构造性偏高的指标，不能证明在线模型也不会幻觉。上线前需要人工抽检和 LLM 模式评测。

### 怎么处理跨域问题？

先做内容词过滤和范围判断；没有内容重叠时明确拒答，不根据常识猜测。

### 为什么用 SSE 而不是 WebSocket？

问答是单向流式输出，SSE 更简单、更容易穿透代理、浏览器原生支持；双向实时协作才需要 WebSocket。

### 如果并发上来怎么办？

SQLite 换 Postgres，限流从进程内换成 Redis，索引服务拆成异步任务，静态资源走 CDN，模型调用加超时、重试和熔断。

### 这个项目最大的不足是什么？

真实用户验证不够，示例政策不是官方数据，评测集只有 32 条。下一步最重要的是社区试点和人工事实核查，而不是继续堆功能。
