# Vibe Coding 记录

这份记录对应 JD 里的「案例与经验沉淀」：记录 AI 工具怎么用、产出了什么、人工怎么审查、最后效果如何。

## 工具与原则

- 使用 ChatGPT / Claude Code 式 AI 编程工具辅助需求拆解、代码骨架、调试和测试。
- AI 负责生成候选实现，人工负责判断、裁剪、验证和负责。
- 不把 API Key、真实客户数据、内部地址发给外部模型。
- AI 生成代码必须经过 diff 阅读、单元测试、真实接口验证。
- 不把「AI 说可以」当作完成标准，完成标准是测试和可复现的运行结果。

## 典型提示词

### 1. 需求拆解

```text
你是一个 AI 应用开发实习生。请把下面这份 JD 拆成 6 个可以在 3 天内验证的小任务。
每个任务写清楚：用户价值、最小实现、验收标准、需要的技术。
不要给我大而全的平台方案。
```

### 2. 政策卡抽取

```text
角色：你是政策翻译助手。
目标：把政策片段改写成居民能照着办的清单。
约束：只依据片段；每条结论标注 [n]；
涉及金额、年龄、时限时提醒以官方为准。
输出：谁能办 / 要带什么 / 怎么办 / 何时截止 / 常见坑。
```

### 3. 代码审查

```text
请以 code reviewer 的身份检查这段 FastAPI 路由：
1. 有没有跨政策串数据；
2. SSE 断流时前端会怎样；
3. 引用编号和来源列表是否一一对应；
4. 有没有未处理的异常和敏感信息。
只列问题和修复建议，不要重写整个文件。
```

## 踩坑记录

### 坑 1：中文口语问句零命中

「多久能办完？」和「办理时限」字面重叠很少，TF-IDF 直接返回空。

修复：问答锁定单政策后，把当前政策片段按原文顺序全部作为上下文；本地回答先识别意图（材料 / 流程 / 时限 / 待遇 / 条件 / 注意事项），再抽字段。

### 坑 2：切块把标题和首条列表合并

原来的切块用空格拼接句子，`## 所需材料` 和 `- 申请表` 被拼成一行，材料段识别失败。

修复：切块改为保留换行；解析器支持「标题 + 首条列表」在同一行时拆开；引用和字段抽取都能识别。

### 坑 3：SSE 跨 chunk 断包

前端按 `\n\n` 切事件，但网络返回可能在任意位置断开。

修复：用缓冲区累积 `TextDecoder` 输出，按 `\r?\n\r?\n` 切完整事件，最后处理残留 buffer。

### 坑 4：引用编号和来源对不上

检索排序会把片段重新排序，`[1]` 未必是来源面板的第 1 段。

修复：问答按原文 `ord` 顺序组装上下文，分数只用于排序；卡片和问答共用同一套来源编号。

### 坑 5：一页纸变成两页

第一次 PDF 第二页多出约 6cm 内容。

修复：压缩重复技术清单、缩短流程说明、调小打印字号和段间距；用 pdfplumber 检查 1 页、文字在页边距内、无重叠。

## 效果

- 4 份示例政策，12 个可追溯片段。
- 本地问答约 0.6-0.8 秒。
- 14 个自动化测试全部通过。
- 桌面 1440px 和手机 390px 无横向溢出。
- 一页纸案例 PDF 为 1 页 A4。
- 演示估算节省约 128 分钟（按人工整理和问答耗时估算，非严格对照实验）。

## 我学到的

- AI 最擅长把「模糊想法」快速变成可运行骨架，但边界条件、数据一致性和验收标准必须人来定。
- 让 AI 先列计划再写代码，比直接说「帮我写完」更容易中途纠偏。
- 对 AI 生成的检索 / 流式 / 引用逻辑，必须用真实问题做端到端验证。
- 记录踩坑比记录「用了什么工具」更有价值，因为踩坑能说明你真的理解代码。
